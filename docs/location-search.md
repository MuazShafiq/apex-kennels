# Search-first transport locations (#93)

Search candidates are not vehicle entrances. Customers search within the same Islamabad/Rawalpindi rectangle enforced by intake, choose a candidate, inspect its Google Maps link, adjust the exact coordinates or paste an exact gate pin, and explicitly confirm the vehicle gate. The pickup and separate drop-off controls have independent cancellation, debounce, results and confirmation state. Existing exact-pin and GPS paths work without search or tiles. No map imagery is required to submit a pasted pin.

The Worker calls Geoapify autocomplete privately with `filter=rect:72.81,33.43,73.3,33.84` and `bias=proximity:73.06,33.65`, as documented in the [official autocomplete API](https://apidocs.geoapify.com/docs/geocoding/address-autocomplete/). It returns at most five bounded local Pakistani results. Provider responses, redirects, size, timeout and unsafe labels are checked. Customer query text and keys are never logged. Provider failures return a fallback instruction. No Google Places service, billing or new paid capacity is provisioned.

## Configuration and usage protection

`POST /api/book/search` requires same origin, a JSON body with only `query` (3–120 characters), the existing private `GEOAPIFY_API_KEY`, the global `LOCATION_SEARCH_BUDGET` namespace, and both Cloudflare rate-limit bindings:

- `LOCATION_SEARCH_RATE_LIMIT`: per trusted `CF-Connecting-IP`, recommended 10 requests / 60 seconds.
- `LOCATION_SEARCH_USAGE_LIMIT`: shared `apex-location-search` key, recommended 30 requests / 60 seconds.

Missing any protection or the private key fails closed with 503. `APEX_LOCATION_SEARCH_DISABLED=true` disables search without rotating the shared route-provider credential. Cloudflare rate limiting applies per Cloudflare location, so the shared edge key alone is not a worldwide daily credit cap.

The SQLite Durable Object `LocationSearchBudget`, accessed only through singleton `search-v1`, atomically reserves at most **250 search calls per UTC day** across edges. Reserve after input/IP/edge validation and before the one provider request; uncertain/provider failures remain consumed, with no retries or refunds. Stored state is only UTC day/count. Corrupt state, clock rollback, storage/binding failure and exhaustion refuse provider work. Preserve namespace/class/singleton identity through deploys and rollbacks; recreating it would reset the allowance. This bounds search calls only: staff routing and other uses of the same Geoapify account still require an account-wide no-charge credit ceiling.

## Automated live production acceptance

The existing `.github/workflows/production-smoke.yml` runs on each `main` push, every six hours, and on manual dispatch. Its new `scripts/check-production-location-search.mjs` step runs **after** the established closed-gate production smoke: it sends a cross-origin request (must fail 403 before Geoapify), followed by exactly **one** same-origin, fixed, non-customer query (`F-10 Markaz`). It requires HTTP 200, a relevant local candidate and bounded coordinates/provider attribution. It uses the deployed Worker's existing protected Geoapify secret, not GitHub secrets, and needs no paid resource. There are no retries, bulk searches, private customer locations or writes. One successful monitoring run consumes one of the 250 daily search reservations and typically one Geoapify geocoding credit. Treat a failing monitor as an actual production investigation, not proof of a successful endpoint. No real-phone/ISP, booking-write, payment or WhatsApp acceptance is implied.
